# Flow: documentation site (`website/`)

## Stack

- Astro `^5.13` + `@astrojs/starlight` `^0.34`, Geist fonts, `sharp`. Its
  own `package.json` and `package-lock.json` (no workspace).
- `astro.config.mjs`: `site: https://RicardoMBregalda.github.io`,
  `base: /aeternis-log/`, `trailingSlash: 'always'`, custom CSS
  (`src/styles/custom.css`), custom `ThemeSelect` component, Expressive Code
  themes (github-dark/light), edit links to `main/website/`, OG image.
- Landing: `src/components/Landing.astro` via `src/content/docs/index.mdx`.
- Content: `src/content/docs/<section>/*.md`, with the sidebar
  **autogenerated per directory**: introduction, getting-started, guides,
  api, sdks, operations, security, commercial, reference.

## Build and deploy

```bash
cd website && npm ci && npm run dev       # http://localhost:4321/aeternis-log/
cd website && npm run build && npm run preview
```

`.github/workflows/deploy-docs.yml` runs on push to `main` touching
`website/**` (or manually): Node 20, `npm ci`, `npm run build`, upload
`website/dist`, then `deploy-pages`. It is the **only** CI workflow in the
repo. No Go or Python tests run in CI, so the local gates (`ship-check`)
are the real quality bar.

For visual work, use the `run` / preview tooling with a `.claude/launch.json`
entry for `npm run dev` and verify in the browser pane. Internal links must
include the `/aeternis-log/` base (Starlight handles this for relative links).

## Product → docs mapping (keep in sync)

| When you change… | Update these pages |
|---|---|
| Hash / Merkle scheme | `security/cryptography.md`, `security/tamper-evidence.md`, `sdks/verification.md`, `introduction/how-it-works.md` |
| Verify semantics / response | `guides/verify-integrity.md`, `api/endpoints.md`, `api/errors.md` |
| Record API (fields, pagination, delete) | `api/endpoints.md`, `guides/create-and-anchor.md`, `getting-started/quickstart.md` |
| Auth / tenancy | `api/authentication.md`, `guides/multi-tenancy.md`, `security/tenant-isolation.md` |
| Public endpoint | `security/threat-model.md`, `guides/verify-integrity.md` |
| Webhook | `guides/webhooks.md` |
| Reports | `guides/audit-reports.md` |
| Config keys / env | `operations/configuration.md` |
| Compose / Helm | `operations/docker-compose.md`, `operations/kubernetes.md` |
| Migrations / chaincode upgrades | `operations/migrations.md`, `operations/chaincode-upgrades.md` |
| Metrics / alerts | `operations/observability.md` |
| Hardening (CORS, limits, headers) | `security/hardening.md`, `operations/hardening-checklist.md` |
| SDK APIs | `sdks/go.md`, `sdks/python.md` |
| Anything user-visible | `reference/changelog.md` |

Also keep `README.md`, `docs/*.md` (runbooks, isolation guarantee) and the
SDK READMEs consistent. Swagger is generated from handler annotations at
image build time and is never hand-edited.

## Rules

- English only. Technical claims must match the code. When in doubt, read
  the flow skill for that area first.
- Public pages must not include internal or business material (pricing
  strategy, internal roadmaps, commercialization plans). The
  `commercial/` section is public-facing. Review it with that lens.
- Don't document known bugs as features. If behavior differs from the docs,
  fix the code or state the limitation honestly.
